# 内容处理流水线

用户丢给你的任何资料（文章、URL、文件、问题），你都要能处理完并整理到知识库。这是"第二大脑"的核心体验。

## 处理流程（6 步）

每次处理内容时，严格按以下 6 步执行：

### Step 1: 创建任务

在用户的 `10_Inbox/<成员名>/00_To-Do.md` 末尾追加一条任务：

```markdown
- [ ] 阅读并总结《标题》 #next
```

或根据内容类型调整描述：
- 文章 → `阅读并总结《文章标题》`
- 调研 → `调研：主题关键词`
- 转换 → `整理为笔记：来源描述`

### Step 2: 执行处理

根据内容类型执行不同操作：

| 类型 | 用户说的 | 你的操作 |
|------|---------|---------|
| 阅读文章 | "帮我读这篇文章" / 发了一个 URL | 阅读全文，提取核心观点，生成结构化摘要 |
| 调研信息 | "帮我查一下 X" / "了解一下 Y" | 搜索相关信息，整理成知识笔记 |
| 格式转换 | "转成 Markdown" / "整理成笔记" | 将内容转为标准 Markdown 笔记格式 |
| 分析内容 | "帮我看看这个" / 发了文件 | 阅读分析，提取要点和行动建议 |

产出统一为 Markdown 格式笔记。

### Step 3: PARA 路由决策

决定笔记保存在哪个目录。按以下顺序判断：

**第一步：扫描已有目录**

查看知识库中已有的目录结构：
```
ls 30_Projects/
ls 20_Areas/
ls 40_Resources/
```

**第二步：按优先级匹配**

| 优先级 | 判断条件 | 存放位置 | 示例 |
|--------|---------|---------|------|
| 1 | 内容与某个已有项目**直接相关** | `30_Projects/<项目名>/` | 数据库优化文章 → `30_Projects/数据库迁移/` |
| 2 | 内容属于用户**长期关注的领域**，且该领域目录已存在 | `20_Areas/<领域>/` | 投资策略文章 → `20_Areas/理财/` |
| 3 | 内容是通用**参考资料、工具、方法论** | `40_Resources/<分类>/` | Kubernetes 教程 → `40_Resources/技术/` |
| 4 | 属于新领域，用户可能持续关注 | `20_Areas/<新领域>/`（新建） | 第一篇健身文章 → `20_Areas/健康/` |
| 5 | 无法判断归属 | `10_Inbox/<成员名>/` | 等下次整理时再归类 |

**判断技巧**：
- 如果用户在对话中提到了项目名 → 直接归入该项目
- 如果内容主题和已有 `20_Areas/` 子目录吻合 → 归入该领域
- 如果是工具文档、教程、方法论 → 大概率 `40_Resources/`
- 不确定？先放 `10_Inbox/`，绝不要猜

### Step 4: 保存笔记

用以下模板保存到目标目录：

```markdown
# 标题

> 来源：URL / 文件名 / 对话上下文
> 处理时间：YYYY-MM-DD
> 标签：#tag1 #tag2

## 摘要

一段话概述核心内容。

## 要点

- 要点 1
- 要点 2
- 要点 3

## 详细笔记

完整的结构化内容。根据原始材料的性质，可以包含：
- 知识点整理
- 操作步骤
- 代码示例
- 对比分析
- 个人见解

## 行动建议

基于内容分析，建议用户可以做什么（如果适用）。

## 相关链接

- [[已有的相关笔记]]
- [[30_Projects/相关项目]]
```

**文件命名**：使用简洁的中文或英文名，如 `Kubernetes入门指南.md`、`投资策略-定投法.md`。

**目录不存在时**：自动创建。例如 `40_Resources/技术/` 不存在，就创建它。

### Step 5: 标记任务完成

回到 Step 1 创建的任务，将 `- [ ]` 改为 `- [x]`：

```markdown
- [x] 阅读并总结《标题》 #next
```

Tasks 插件会自动加上 `✅ YYYY-MM-DD`。

### Step 6: 写 Journal 日志

在 `10_Inbox/Agents/Journal.md` 末尾追加：

```markdown
### YYYY-MM-DD HH:mm — 处理内容：标题

处理了用户提供的 [类型]。
摘要：一句话总结。
保存位置：[[目标路径/文件名]]
```

## 常见场景示例

### 场景 1：用户发了一篇文章 URL

```
用户："帮我看看这篇文章 https://example.com/article"

Agent 执行：
1. To-Do 追加：- [ ] 阅读并总结《文章标题》 #next
2. 阅读文章，生成结构化笔记
3. ls 30_Projects/ 20_Areas/ 40_Resources/ → 发现 40_Resources/技术/ 存在
4. 保存到 40_Resources/技术/文章标题.md
5. To-Do 标记完成：- [x] 阅读并总结《文章标题》 #next
6. Journal 记录：处理了文章，保存在 40_Resources/技术/
```

### 场景 2：用户要求调研某个话题

```
用户："帮我了解一下 RAG 是什么，我在做 AI 项目"

Agent 执行：
1. To-Do 追加：- [ ] 调研：RAG 技术概述 #next
2. 搜索并整理 RAG 相关知识
3. 用户提到了"AI 项目" → 检查 30_Projects/ 是否有 AI 相关项目
   → 有 30_Projects/AI项目/ → 归入该项目
4. 保存到 30_Projects/AI项目/RAG技术调研.md
5. To-Do 标记完成
6. Journal 记录
```

### 场景 3：用户发了一个文件要求整理

```
用户："帮我把这个会议纪要整理成笔记"（附带文件内容）

Agent 执行：
1. To-Do 追加：- [ ] 整理为笔记：会议纪要 YYYY-MM-DD #next
2. 提取会议要点、决策、行动项
3. 判断归属：会议和哪个项目相关？
   → 内容涉及"网站重构" → 30_Projects/网站重构/
4. 保存到 30_Projects/网站重构/会议纪要-YYYY-MM-DD.md
5. 额外：将会议中的行动项追加到 To-Do
6. To-Do 标记原任务完成
7. Journal 记录
```

### 场景 4：用户的请求产生了有价值的输出

```
用户："帮我写一份技术方案"（对话中产出了文档）

Agent 执行：
1. To-Do 追加：- [ ] 撰写技术方案：XXX #next
2. 在对话中完成技术方案撰写
3. 判断归属：这是项目交付物 → 30_Projects/<项目名>/
4. 保存到 30_Projects/<项目名>/技术方案-XXX.md
5. To-Do 标记完成
6. Journal 记录：撰写了技术方案，保存位置
```

## 何时触发内容处理

以下情况自动进入内容处理流水线：

1. 用户发了 URL 并要求处理
2. 用户说"帮我读/看/总结/分析..."
3. 用户说"帮我查/了解/调研..."
4. 用户说"转成笔记/整理成 Markdown"
5. 用户发了文件/文档内容
6. 对话中产出了有价值的文档/代码/分析

第 6 点很重要：即使用户没有显式说"帮我记下来"，只要对话产出了值得保存的内容，Agent 就应该主动提议保存到知识库。
